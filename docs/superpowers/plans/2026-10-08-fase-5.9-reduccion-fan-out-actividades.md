# Fase 5.9 — Reducción del fan-out del catálogo de actividades

> **For agentic workers:** REQUIRED SUB-SKILL: Use `executing-plans` to implement this plan task-by-task. Steps use checkbox (`- [x]`) syntax for tracking.

**Goal:** cargar tarjetas y selectores desde los listados paginados y consultar el detalle únicamente al abrir una actividad.

**Architecture:** el catálogo administrativo devuelve un modelo de resumen (`ActivitySummary`) sin campos exclusivos del detalle. Los hooks de detalle conservan sus consultas independientes y sus claves pública o privada. TanStack Query sigue administrando la caché.

**Tech Stack:** React 19, TypeScript 6, TanStack Query 5, Vitest 5, Storybook 10, Playwright.

---

## Contrato verificado (2026-10-08, backend vivo)

- `GET /api/v1/activities` es público y pagina; cada `ActivityListItem` embebe aula, programa y unidad y **no** expone `equipment`, `enrolledCount`, `checkedInCount` ni `cancelReason`.
- `GET /api/v1/event-programs/{id}/activities` pagina por programa; cada `EventProgramActivityItem` tampoco expone los campos de detalle.
- `GET /api/v1/activities/{id}` devuelve `ActivityDetail` con `equipment`, `enrolledCount`, `checkedInCount` y `cancelReason`.

**Decisión aprobada:** inscritos y equipamiento se consultan en el detalle; los totales sin contrato agregado se muestran como «No disponible».

**Presupuesto de peticiones:** el catálogo compuesto pasa de `páginas + N detalles` a solo `páginas` de listados. La agenda pública y el listado por programa ya cumplían.

## Evidencia de cierre — 2026-10-08

- **Contrato verificado contra el backend vivo:** `GET /api/v1/activities`,
  `GET /api/v1/event-programs/{id}/activities` y `GET /api/v1/activities/{id}`. Los dos listados no
  exponen `equipment`, `enrolledCount`, `checkedInCount` ni `cancelReason`; solo el detalle los
  publica. `pnpm run api:mocks-check` pasó con 402 verificaciones en 55 operaciones.
- **Modelo (T1):** `ActivitySummary` es un `Omit` de `Activity` sin los cuatro campos de detalle y
  `ActivityCatalog.activities` lo usa. `toActivitySummary` proyecta con allowlist y copia los
  ponentes; sus pruebas fijan la ausencia de campos y la independencia de referencias.
- **Catálogo API (T2):** `readCatalogActivitiesPage` reutiliza `mapActivitiesListPage` y añade las
  referencias planas `classroomId`/`eventProgramId`; `apiActivityCatalogAdapter` recorre solo las
  páginas de listados y nunca pide `GET /api/v1/activities/{id}`. El presupuesto se prueba con 0, 1,
  50, 51 y 120 actividades y con varios programas: `Math.max(1, totalPages)` peticiones de listado y
  cero detalles.
- **Mocks (T3):** API y mock comparten la misma proyección; el mock conserva el registro completo
  (`satisfies ActivityCatalog`) para que detalles, reservas de aulas y scopes sigan viendo
  `Activity`. Ambos composition roots verifican que el resumen no lleva equipo y que `getActivity`
  conserva contadores.
- **Selectores y métricas (T4):** `ActivityRow.activity` es `ActivitySummary`;
  `CatalogSummary.enrolledCount` y `ProgramSummary.enrolledCount` son `number | null` y valen `null`
  porque el contrato no publica un agregado. `sumEnrolledCount` se retiró del modelo, del barrel y
  de las pruebas; `useReportsOverview` documenta `enrolledCount: number | null` y cubre el scope con
  su propia prueba.
- **UI (T5):** `ActivityCard` pierde `showEnrolledCount`/`showEquipment` y gana el enlace «Ver
  detalle» a la ruta administrativa; `EventProgramCard` muestra «No disponible»; el catálogo, el
  dashboard, asistencia y reportes dejaron de fabricar ceros. `App.test.tsx` ya no afirma el conteo
  de inscritos.
- **Presupuesto (T6):** `ActivityCatalogLoading.integration.test.tsx` monta el adapter API real
  sobre un fetcher controlado y recorre cargar, buscar, paginar, expandir descripción y seleccionar
  contexto con cero peticiones de detalle; abrir el detalle administrativo produce exactamente una.
  Validado por mutación: con `detailRequests` forzado a lista vacía, la aserción de una petición
  falla.
- **Puertas:** `pnpm run verify:quick` verde (232 archivos, 1.898 pruebas); `pnpm run test:storybook`
  verde (252 comparaciones con `play`, axe y visual); `pnpm run check` verde (formato, lint, tipos,
  suite, build, Storybook e inventario); `pnpm run components:inventory:check` verde.
- **Visual deliberado:** baselines de `ActivityCard`, `EventProgramCard` y las tres stories nuevas de
  `ActivityCatalogView` regenerados tras revisar las capturas; se eliminó el baseline huérfano de
  `WithEnrollmentCount` y se agregó `WithAttendeeTotal`.
- **Desviaciones:** `ReportsOverviewReport` se declara explícitamente porque el literal `null`
  activaba `no-unnecessary-condition`; las tarjetas usan `??` para el total ausente; `App.test.tsx`
  perdió la aserción de inscritos al no existir ya el dato.
- **Documentación:** ADR-0016 (supersede ADR-0005, que queda con estado `Superseded`),
  `docs/adr/README.md`, `CONTEXT.md`, `spec/activities/activities-features.md`,
  `docs/components/README.md` e inventario.
