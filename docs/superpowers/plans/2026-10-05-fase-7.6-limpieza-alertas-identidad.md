# Fase 7.6 - Limpieza de alertas por identidad - Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [x]`) syntax for tracking.

**Goal:** Garantizar que login, logout o cambio de usuario descarten toda alerta cacheada, incluidos los
resultados y errores tardios de acciones que pertenecian a una sesion ya descartada, incluso cuando la
cuenta nueva es la misma.

**Architecture:** Una generacion de sesion monotona y en memoria en `useSessionStore` distingue cada
instancia de sesion. `useAlertReadMutations` fija la generacion al iniciar una accion y la verifica en
`onMutate`, `onError` y `onSettled`, de modo que una mutacion que sobrevive a un logout o a un cambio de
cuenta no escribe, no restaura y no invalida la cache de la sesion viva. La limpieza de datos ya existe
(`queryClient.clear()` en login, logout y fin de sesion); esta fase la demuestra con alertas y cierra el
unico hueco real: los callbacks tardios que comparaban solo el `userId`.

**Tech Stack:** React 19, TypeScript 6, TanStack Query 5, Zustand 5, Vitest 5, Testing Library.

**Contrato verificado contra el backend vivo el 2026-10-05:** sin cambios. La fase no introduce,
modifica ni elimina operaciones HTTP. `GET /api/v1/alerts` toma el destinatario del token, de modo que
el frontend no puede cambiar de identidad por parametro; la limpieza es una garantia local de cache y
no aplica `api:mocks-check`.

**Decisiones registradas:**

- **La generacion vive en el store:** `setSession` la avanza cuando la identidad entrante es distinta
  de la actual (incluido `null`), `clearSession` y `endSession` la avanzan siempre. Una renovacion de
  token o una edicion de perfil conservan el mismo valor porque no son una sesion nueva. No se
  persiste, no viaja en claves de Query y no es PII.
- **Desviacion registrada durante la ejecucion:** se agrego la accion
  `advanceSessionGeneration()` y `clearPreviousIdentityState` la invoca tras limpiar la cache. Cierra
  el caso de un login que reemplaza la sesion viva con la misma identidad, donde `setSession` no
  cambia la generacion; sin el aviso, un callback en vuelo de la sesion reemplazada podia restaurar
  su snapshot sobre la cache recien limpiada.
- **El guard usa identidad y generacion:** el `userId` acota la cache y la generacion distingue dos
  accesos seguidos de la misma cuenta. Con solo el `userId`, un fallo tardio tras logout y re-login
  restauraba el snapshot anterior sobre la cache limpia.
- **Consultas en vuelo quedan cubiertas por `queryClient.clear()`:** al destruir la consulta, TanStack
  Query cancela su fetch y descarta la respuesta tardia. Se fija con una prueba para que una
  actualizacion de la libreria que cambie esa conducta no pase inadvertida.
- **Las mutaciones no se pueden cancelar:** TanStack Query no cancela una mutacion en vuelo y sus
  callbacks siguen ejecutandose tras `clear()`. Por eso el guard es imprescindible y no basta con la
  limpieza de cache.
- **Sin cambios visuales ni de rutas:** no hay componentes, stories, baselines ni inventario
  afectados.
- **Sin persistencia:** las alertas siguen fuera de `PERSISTED_QUERY_KEY_ROOTS`.

```ts
    })),

      sessionGeneration: state.sessionGeneration + 1,

  setSession: ({ currentUser, tokens }) =>
    set((state) => ({
      currentUser,

      tokens,
```

En `src/features/alerts/hooks/useAlertReadMutations.ts`:

1. `inFlightRef` pasa a recordar la generacion:

```ts
const inFlightRef = useRef<{ sessionGeneration: number } | null>(null);
```

2. Las variables incorporan la generacion y el helper verifica ambas cosas:

```ts
type AlertReadVariables = {
  intent: AlertReadIntent;
  userId: string;
  sessionGeneration: number;
};

/**
 * Una accion solo escribe si la identidad y la generacion capturadas al iniciarla siguen siendo las
 * de la sesion viva. La generacion distingue dos accesos de la misma cuenta, caso que el `userId`
 * por si solo no puede detectar.
 */
function isCurrentIdentity(userId: string, sessionGeneration: number): boolean {
  const state = useSessionStore.getState();

  return (
    (state.currentUser?.id ?? ANONYMOUS_USER) === userId &&
    state.sessionGeneration === sessionGeneration
  );
}
```

3. Los callbacks reciben y verifican la generacion:

```ts
    onError: (_error, { sessionGeneration, userId }, context) => {
      if (!isCurrentIdentity(userId, sessionGeneration)) return;

      for (const [key, page] of context?.snapshots ?? []) {
        queryClient.setQueryData(key, page);
      }
    },
    onMutate: async ({ intent, sessionGeneration, userId }) => {
      await queryClient.cancelQueries({ queryKey: queryKeys.alertsScope(userId) });

      if (!isCurrentIdentity(userId, sessionGeneration)) return { snapshots: [] };
      // ...sin cambios en el snapshot y la escritura optimista
    },
    onSettled: (_data, _error, { sessionGeneration, userId }) => {
      if (!isCurrentIdentity(userId, sessionGeneration)) return;

      void queryClient.invalidateQueries({ queryKey: queryKeys.alertsScope(userId) });
    },
```

4. `run` captura la generacion, la asocia al bloqueo y la envia como variable:

```ts
const run = async (intent: AlertReadIntent): Promise<unknown> => {
  const { currentUser, sessionGeneration } = useSessionStore.getState();
  const userId = currentUser?.id ?? ANONYMOUS_USER;

  if (inFlightRef.current?.sessionGeneration === sessionGeneration) return undefined;

  inFlightRef.current = { sessionGeneration };
  try {
    return await mutation.mutateAsync({ intent, sessionGeneration, userId });
  } catch {
    // El fallo se expone por `error`; la vista muestra el copy localizado.
    return undefined;
  } finally {
    if (inFlightRef.current?.sessionGeneration === sessionGeneration) {
      inFlightRef.current = null;
    }
  }
};
```
