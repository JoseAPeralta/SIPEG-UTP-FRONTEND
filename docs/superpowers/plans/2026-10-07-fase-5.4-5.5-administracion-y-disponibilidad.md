# Fases 5.4 y 5.5 Administracion De Actividades Y Disponibilidad Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Entregar la administracion de actividades por programa con formularios de alta y edicion y un selector de aula que conserva la seleccion y el formulario ante conflictos `409`.

**Architecture:** `features/activity-catalog` suma un puerto administrativo (`ActivitiesAdapter`) con mapper y adapter API propios, un registro mock compartido por composicion y hooks de pagina, detalle, capacidades y mutaciones. La UI vive en rutas por programa compartidas entre `/admin` y `/operaciones`, y el selector de aulas existente gana criterios vigentes y aula asignada. La disponibilidad sigue siendo una lectura publica explicita y el backend conserva la validacion final.

**Tech Stack:** React 19, TypeScript 6, Chakra UI 3, TanStack Query 5, Vitest 5, Testing Library, Storybook 10 y Playwright.

## Contrato verificado

Consultado el 2026-10-07 contra el backend vivo:

| Operacion                                    | Auth    | Uso                                                               |
| -------------------------------------------- | ------- | ----------------------------------------------------------------- |
| `GET /api/v1/event-programs/{id}/activities` | Bearer  | Pagina filtrada (`status=ALL` solo autorizado)                    |
| `GET /api/v1/activities/{id}`                | Bearer  | Detalle con equipo y contadores                                   |
| `POST /api/v1/activities`                    | Bearer  | Alta en borrador dentro de un programa ACTIVE                     |
| `PATCH /api/v1/activities/{id}`              | Bearer  | Parche parcial; `ONGOING`/`COMPLETED`/`CANCELLED` responden `409` |
| `GET /api/v1/classrooms/available`           | Publica | Disponibilidad por fecha, horario, capacidad, tipo y una amenidad |

- Los ponentes viajan inline (`ActivitySpeakerInput`); el detalle devuelve solo `id`, `firstName` y `lastName`.
- La capacidad de escritura es `maxCapacity`; la de lectura, `capacity`.
- `eventProgramId` se fija al crear y es inmutable al editar.
- El contrato admite `CONFERENCE_ROOM` como tipo de aula; el frontend no lo conocia.

## Decisiones de alcance

- La administracion es por programa: una sola pantalla compartida evita duplicar flujos entre ADMIN y colaboradores.
- Las capacidades salen del descubrimiento de scopes; la UI solo deja de ofrecer acciones y el backend decide.
- La edicion envia un diff: un cambio de descripcion no revalida la reserva ni reenvia ponentes, correo u organizacion.
- La actividad que edita su propia reserva no puede excluirse en `GET /classrooms/available`; el selector la conserva etiquetada como asignada y el `PATCH` valida al guardar.

## Evidencia y desviaciones

- El contrato vivo confirmo las cinco operaciones y el desfase de `CONFERENCE_ROOM`; `pnpm run api:mocks-check` paso con 356 verificaciones en 51 operaciones.
- `pnpm test`: 219 archivos y 1.688 pruebas en verde; `pnpm run lint` y `pnpm run typecheck` sin hallazgos.
- `pnpm run test:storybook`: 53 suites y 224 pruebas con `play`, axe y comparacion visual. Se agregaron 9 stories (`ActivityForm` x3, `ProgramActivitiesView` x3, `ActivityDetailView` x3, mas `ClassroomAvailabilitySelector--AssignedClassroomKept`) y se regeneraron los baselines de `OperationalScopeView` y `EventProgramsView` tras revisarlos.
- Desviacion deliberada: la creacion envia `speakers` inline y la edicion reemplaza la lista solo cuando la persona los edita; el detalle no devuelve correo ni organizacion y reenviarlos habria perdido esos datos.
- Desviacion deliberada: un parche que no toca horario, capacidad, aula ni estado no revalida la reserva en el mock; de lo contrario los fixtures historicos con ventanas incompletas bloquearian la edicion de una descripcion.
- El runtime del harness local no esta disponible en esta maquina (no hay modelo local; solo el ejecutable de OpenCode), asi que la ejecucion se hizo en el workspace principal y no a traves de `scripts/run-agent-sandbox.sh`.
- Pendiente de fases siguientes: publicar/cancelar (5.6), eliminacion (5.7), notificacion (5.8), reduccion del fan-out (5.9) e invalidacion ampliada (5.10).
