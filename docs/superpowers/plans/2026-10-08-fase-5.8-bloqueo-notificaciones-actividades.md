# Fase 5.8 — Bloqueo de notificaciones no respaldadas por el contrato

> **Para la ejecución:** utilizar `executing-plans` y completar las tareas con sus verificaciones.
> Los pasos usan casillas (`- [ ]`) para seguimiento.

**Goal:** garantizar que la administración de actividades no presente decisiones ni resultados de
notificación que el backend todavía no haya contratado.

**Architecture:** conservar los requests y las confirmaciones existentes, reforzando las allowlists,
las pruebas de interfaz y los mensajes de resultado. El checker contractual detectará cambios que
obliguen a revisar este bloqueo. La funcionalidad de notificaciones se habilitará únicamente cuando
la operación propietaria publique sus entradas y comportamiento.

**Tech Stack:** TypeScript 6, React 19, Vitest, Testing Library, Storybook y la CLI OpenAPI del
proyecto.

---

## 1. Alcance y contrato verificado

El apartado 5.8 establece:

> No mostrar `notifyAttendees` hasta que el backend defina campo, obligatoriedad y resultado.

Se relaciona con **`NTF-002`**, decisión de notificar asistentes, y **`NTF-004`**, presentación
honesta del resultado.

### Evidencia del contrato vivo

Consultado el **2026-10-08**:

| Operación                             | Entrada publicada           | Resultado publicado        | Notificación                          |
| ------------------------------------- | --------------------------- | -------------------------- | ------------------------------------- |
| `POST /api/v1/activities`             | Datos de alta               | `201` con `ActivityDetail` | Sin intención ni resultado contratado |
| `PATCH /api/v1/activities/{id}`       | Campos editables y `status` | `200` con `ActivityDetail` | Sin intención ni resultado contratado |
| `POST /api/v1/activities/{id}/cancel` | Motivo opcional             | `200` con `ActivityDetail` | Sin intención ni resultado contratado |
| `DELETE /api/v1/activities/{id}`      | Sin cuerpo                  | `204` sin cuerpo           | Sin intención ni resultado contratado |

Las búsquedas dirigidas de `notifyAttendees` y `notification` no devolvieron operaciones. La
revisión de las operaciones anteriores confirmó que:

- Ningún request declara `notifyAttendees`.
- Los cuerpos JSON publicados usan `additionalProperties: false`.
- `ActivityDetail` no declara resultados de envío, entrega, cola o destinatarios.
- `DELETE` no admite cuerpo.
- El envelope contiene un `message` de texto libre, que no debe convertirse en una promesa de
  notificación.

**Conclusión:** 5.8 debe cerrar el bloqueo y su cobertura; la experiencia de notificación continúa
pendiente de contrato.

La ausencia de estos campos **no permite afirmar** que el backend jamás realice comunicaciones
automáticas.

## 2. Estado actual y dependencias

En el código revisado:

- `CreateActivityRequest` y `UpdateActivityRequest` no contienen `notifyAttendees`.
- El adapter reconstruye los cuerpos con allowlists.
- `ActivityForm` no tiene controles de notificación.
- La edición anuncia únicamente que se guardaron los cambios.
- Las fases 5.6 y 5.7 tienen planes creados; su implementación todavía no aparece en el código
  inspeccionado.

Para cerrar la cobertura completa de 5.8, ejecutar después de integrar 5.6 y 5.7, incluyendo sus
confirmaciones y comandos de cancelación y eliminación.

### Decisiones de implementación

1. Mantener ausente la opción de notificar para ADMIN y colaboradores.
2. No enviar tampoco `notifyAttendees: false`: sigue siendo un campo ajeno al contrato.
3. No añadir una capacidad, estado global o feature flag de notificación para representar una
   función inexistente.
4. Confirmar únicamente alta, edición, publicación, despublicación, cancelación o eliminación.
5. Conservar el motivo de cancelación y la explicación de retención: son datos contractuales
   distintos de una decisión de comunicación.
6. No interpretar la existencia de alertas ni el número de inscritos como autorización para ofrecer
   notificaciones.
