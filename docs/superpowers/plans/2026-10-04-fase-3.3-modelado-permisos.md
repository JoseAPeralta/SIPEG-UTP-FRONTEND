# Fase 3.3 - Modelado de permisos

> **For agentic workers:** REQUIRED SUB-SKILL: Use `executing-plans` to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Crear el modelo frontend canonico de roles de colaboracion (`VIEWER`, `EDITOR`, `ORGANIZER`) y del catalogo de permisos, con etiquetas en espanol y deteccion automatica de divergencias frente a OpenAPI.

**Architecture:** Un modulo nuevo `features/collaboration` con tipos, catalogos `as const` y funciones puras (`type guards` y resolucion de etiquetas). No duplica la matriz interna de permisos predeterminados por rol ni decide autorizacion: el backend sigue siendo la autoridad. La UI futura (3.6-3.8) consume `resolvePermissionLabel` y nunca un codigo crudo.

**Tech Stack:** React 19, TypeScript 6, Vitest y la CLI `api:contract` para contraste con OpenAPI.

---

## Contrato verificado (backend vivo, 2026-10-04)

- Roles en `POST /event-programs/{id}/collaborators`, `PATCH /event-programs/{id}/collaborators/{userId}` y sus equivalentes de actividad: `VIEWER | EDITOR | ORGANIZER`.
- Permisos en `POST /event-programs/{id}/permissions`, `POST /activities/{id}/permissions` y `DELETE .../permissions/{permission}`: 21 valores canonicos.
- `GET /users/me/permissions` y los listados de colaboradores devuelven `name` como `string` libre, no como enum: el catalogo canonico solo se enumera en los cuerpos de las mutaciones.
- `CollaboratorPermission.source`: `ROLE_DEFAULT | OVERRIDE`.
- `CollaboratorListPermission.origin`: `LOCAL | INHERITED | BOTH`.
- OpenAPI **no** publica la matriz de permisos predeterminados por rol; el frontend no la infiere.
