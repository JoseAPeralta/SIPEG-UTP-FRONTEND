# Fase 2.4 Administracion De Aulas Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Permitir que ADMIN liste, filtre, cree, consulte, edite, desactive/reactive aulas, administre sus amenidades y represente su disponibilidad semanal, sin inventar una operacion que el contrato no publica.

**Architecture:** `features/classrooms` conserva la lectura publica del catalogo y suma comandos autenticados al mismo puerto `ClassroomsAdapter`. Los adapters validan cada envelope antes de exponerlo, los hooks aisan las fronteras publica y administrativa por `userId`, y las vistas traducen el estado HTTP a mensajes de producto sin mostrar codigos ni mensajes del backend.

**Tech Stack:** React 19, TypeScript 6, Chakra UI 3, TanStack Query 5, React Router 8, Vitest 5, Testing Library y Storybook 10.

| `POST /api/v1/classrooms/{id}/availability`                    | `bearerAuth` ADMIN | `201 ClassroomDetail` | `400`, `401`, `403`, `404`, `409` |
| `DELETE /api/v1/classrooms/{id}/availability/{availabilityId}` | `bearerAuth` ADMIN | `200 ClassroomDetail` | `400`, `401`, `403`, `404`        |

- Filtros del listado: `page`, `limit` (maximo 50), `type`, `minCapacity`, `amenity`, `isActive`.
  Sin `isActive` el backend devuelve **solo aulas activas**: el panel necesita las inactivas para
  reactivarlas, de modo que el adapter recorre dos listas cuando el filtro es `"all"`.
- `ClassroomSummary` no lleva `availability`; `ClassroomDetail` si, y exige las nueve propiedades.
- `CreateClassroom` exige `name` (1-50), `type` y `capacity` (> 0); `building` (max 50) y `floor`
  (-5 a 100) son opcionales y admiten `null`.
- `UpdateClassroom` es parcial y exige al menos un campo. Desactivar se rechaza con `409` mientras
  haya actividades `SCHEDULED` u `ONGOING` reservando el aula.
- Amenidades duplicadas se rechazan con `409` sin distinguir mayusculas; la busqueda de la
  eliminacion tambien es insensible a mayusculas.
- `AddClassroomAvailability` exige `dayOfWeek` (ISO `1` lunes a `7` domingo) y horas `HH:mm`.
  Las ventanas que se solapan en el mismo dia se rechazan con `409`.
- **No existe `DELETE /api/v1/classrooms/{id}`.** El "borrado" del ciclo de vida es
  `PATCH { isActive: false }`, exactamente como en la Fase 2.2 con unidades.
- `GET /api/v1/classrooms/available` pertenece a la **Fase 2.5** y no se consume aqui.

### Desviaciones

- **No existe `DELETE /api/v1/classrooms/{id}`.** El ciclo de vida se resuelve con
  `PATCH { isActive }`, como las unidades en 2.2, y no se expone ninguna accion de borrado.
- **`GET /api/v1/classrooms/available` no se consume.** Pertenece a la Fase 2.5 y su contrato no se
  necesita para administrar el inventario.
- **`CreateClassroom` acepta `isActive` pero el frontend no lo envia.** El alta es siempre de un aula
  activa y el cambio de estado documentado es el `PATCH`; omitir un campo opcional no altera el
  contrato.
- **`ClassroomSummary` y `ClassroomDetail` son tipos distintos** porque solo el detalle trae
  `availability`. El listado publico sigue usando el resumen.
- **El filtro de estado es triestado (`active`/`all`/`inactive`) y no un booleano.** El contrato solo
  admite `"true"` y `"false"`, y omitirlo significa "solo activas", de modo que un booleano con
  `undefined` seria ambiguo en un sentido que el backend no comparte.
- **El detalle se declara publico pero se mantiene en dos fronteras de cache**, porque el panel debe
  poder invalidar la suya sin tocar la de la agenda y una escritura administrativa nunca debe llegar
  a la vista publica.
- **El detalle no se persiste** en `PERSISTED_QUERY_KEY_ROOTS`: la agenda publica no lo lee y el
  horario semanal en disco seria dato obsoleto sin beneficio.
- **`useClassroomMutations` expone el fallo por area.** Un `409` significa aula reservada, amenidad
  repetida o ventana solapada; la primera version mostraba un unico `failure` en las tres secciones
  y hacia que la misma explicacion apareciera tres veces.
- **Los comandos se declaran con un unico objeto de variables.** `mutateAsync` de TanStack
  interpreta el segundo argumento como opciones de la mutacion, de modo que una firma variadica
  deliveraba la amenidad como objeto de opciones en lugar de como valor.
- **Se saldaron tres deudas de lint preexistentes** en `deferredAdapter.test.ts`,
  `createBrowserAppAdapters.test.ts` y `QueryDevtools.tsx` porque `pnpm run check` es puerta de
  cierre y fallaba antes de esta fase.
- **Se corrigio un defecto latente del fixture de `api:mocks-check`:** indexaba las operaciones solo
  por path, de modo que registrar `POST /api/v1/classrooms` eliminaba el `GET` del mismo path.
- **No se genero story de pagina.** Las dos vistas tienen story, baseline y `play`; las rutas se
  cubren con `App.test.tsx`, igual que en 2.3.
