# Fase 5.7 — Eliminación de actividades bajo la regla de retención

> **Para la ejecución:** utilizar `executing-plans`, completar las tareas con sus verificaciones y
> conservar el seguimiento mediante casillas (`- [ ]`).

**Objetivo:** habilitar la eliminación únicamente para borradores de programas activos y usuarios
autorizados, respetando la retención de asistencia y alertas que verifica el backend.

**Arquitectura:** ampliar `ActivitiesAdapter` con una operación que devuelve `Promise<void>`,
resolver la disponibilidad de la acción mediante permisos y estado, y reutilizar la confirmación del
ciclo de vida prevista en 5.6. La eliminación actualizará las consultas y el contexto de trabajo, y
llevará al usuario a un destino accesible.

**Stack:** React 19, TypeScript 6, Chakra UI v3, TanStack Query v5, Vitest, Testing Library y
Storybook.

---

## 1. Resultado de la revisión contractual

**El bloqueo contractual de 5.7 ya puede levantarse:** el OpenAPI vivo publica la operación y su
regla de retención.

### Operación confirmada

```http
DELETE /api/v1/activities/{id}
Authorization: Bearer …
```

- **Request:** sin cuerpo.
- **Respuesta correcta:** `204`, sin cuerpo.
- **Autorización:** ADMIN o permiso efectivo `activity:delete`.
- **Estados admitidos:** únicamente actividad `DRAFT` dentro de un programa `ACTIVE`.
- **Retención:** la actividad no puede tener registros de asistencia ni alertas.
- **Conflicto:** cualquier incumplimiento de la regla devuelve `409`.
- **Eliminación física:** desaparecen equipo, vínculos de ponentes y colaboraciones locales.
- **Ponentes:** sus entradas de catálogo se conservan.
- **Programas archivados:** sus actividades no se eliminan.
- **Errores documentados:** `400`, `401`, `403`, `404` y `409`.

El contrato menciona que `activity:delete` es un permiso predeterminado de ORGANIZER. La interfaz
seguirá comprobando el **permiso efectivo**, porque puede existir una concesión o revocación
específica.

### Limitación de la lectura actual

`ActivityDetail` no expone la existencia completa de alertas ni una propiedad de elegibilidad para
eliminar.

Por tanto:

- La UI puede determinar **permiso, estado de actividad y estado del programa**.
- El backend confirma la ausencia de historial al recibir `DELETE`.
- Tener contadores en cero no demuestra por sí solo que se cumple toda la retención.
- La interfaz no consultará la bandeja personal de alertas para intentar reconstruir esa regla.

## 2. Dependencias y decisiones

La fase se apoya en la administración de 5.4–5.5 y en la composición prevista para 5.6.

**Estado observado:** 5.6 tiene un plan creado, pero su implementación todavía no aparece en el
código revisado. Al ejecutar 5.7, verificar primero su cierre y reutilizar:

- La confirmación de ciclo de vida.
- La exclusión entre edición y confirmación.
- La resolución del programa padre para colaboradores con acceso directo a una actividad.
- Los mocks que comparten el registro mutable.
- La invalidación del detalle público y del descubrimiento operativo.

### Matriz de disponibilidad

| Condición                                                               | Acción «Eliminar borrador»                    |
| ----------------------------------------------------------------------- | --------------------------------------------- |
| ADMIN, actividad `DRAFT`, programa `ACTIVE`                             | Disponible; el servidor verifica la retención |
| Colaborador con `activity:delete`, actividad `DRAFT`, programa `ACTIVE` | Disponible; el servidor verifica la retención |
| Solo `activity:update` o `activity:cancel`                              | No disponible                                 |
| Permiso vencido o futuro                                                | No disponible                                 |
| Actividad `SCHEDULED`, `ONGOING`, `COMPLETED` o `CANCELLED`             | No disponible                                 |
| Programa no activo                                                      | No disponible                                 |
| Programa o permisos sin resolver, o consulta fallida                    | No disponible                                 |

### Comportamiento de la confirmación

- Botón de apertura: **«Eliminar borrador»**.
- Confirmación identificada con el nombre de la actividad.
- Explicación: **«El borrador se eliminará de forma permanente. Solo puede eliminarse si no tiene
  registros de asistencia ni alertas; el servidor verificará esta condición.»**
- Acciones: **«Eliminar borrador»** y **«Volver sin cambios»**.
- Sin campo de motivo: el contrato no lo acepta.
- Tras `409`, conservar la confirmación y ofrecer actualización de datos.
- La cancelación, cuando esté permitida, será una acción explícita del usuario; un fallo de
  eliminación nunca la ejecutará automáticamente.
