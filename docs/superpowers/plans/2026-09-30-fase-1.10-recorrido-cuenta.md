# Fase 1.10 - Cobertura Del Recorrido De Cuenta - Plan De Implementacion

> **For agentic workers:** REQUIRED SUB-SKILL: Use `writing-plans` to create the detailed plan for
> each phase and `executing-plans` to implement it task-by-task. Steps use checkbox (`- [ ]`) syntax
> for tracking.

**Goal:** Cerrar el punto 1.10 del plan maestro con pruebas que recorran registro -> verificacion ->
login -> datos de la cuenta -> edicion de perfil -> seguridad de la cuenta -> cambio de contrasena ->
logout sobre la aplicacion real, y que comprueben ademas que cada seccion del area personal se alcanza
de forma independiente desde el submenu.

**Architecture:** Una nueva prueba de integracion `src/App.accountJourney.test.tsx` monta `App` con
sus formularios, rutas, hooks y stores reales, e inyecta adapters controlados que responden como una
identidad `USER` coherente. El unico limite del doble es HTTP: todo lo demas - router, formularios,
validacion, `useLogin`, `useProfile`, `useChangePassword`, `useLogout`, `useSessionStore` y la
persistencia - se ejercita sin sustituir. La segunda parte completa la matriz de navegacion del
submenu en `src/App.test.tsx` y anade la unica prueba que faltaba: atras y adelante del historial real
del router, en lugar de pulsar enlaces y llamarlo historial.

**Tech Stack:** React 19, TypeScript 6, Chakra UI 3, React Router 8, TanStack Query 5, Zustand 5,
Vitest 5, Testing Library.

---

## Alcance Y Decisiones

- **Sin cambio de contrato:** la fase no introduce, modifica ni elimina peticiones HTTP, ni campos,
  estados ni enums. No se consulta OpenAPI y no aplica `pnpm run api:mocks-check`.
- **Sin produccion salvo defecto:** la fase escribe pruebas. Si una prueba falla, se distingue entre
  un defecto del arnes y un defecto del producto. Solo en el segundo caso se toca codigo de
  produccion, y siempre con la reproduccion conservada.
- **Integracion de frontend, no E2E:** el recorrido corre en jsdom contra adapters controlados. La
  entrega real del correo de verificacion y la revocacion de otras sesiones necesitan dos sesiones
  reales del backend y pertenecen a la suite E2E de la Fase 12, punto 12.7.
- **La sesion la establece el producto:** la prueba nunca escribe en `useSessionStore` para entrar.
  Se llega a `/perfil/datos` unicamente porque el login del frontend funciono, que es justamente lo
  que el recorrido debe demostrar.
- **El enlace del correo es otra carga de pagina:** `VerifyEmailPage` lee el token de
  `window.location`, no del router. Representarlo exige desmontar y volver a montar `App` en
  `/verify-email?token=...`, que es lo que hace una persona al abrir el enlace. El primer montaje se
  desmonta explicitamente para que no queden dos arboles en `document.body`.
- **El historial se maneja con una sonda, no con una regla:** la nueva prueba monta
  `<App />` junto a una sonda que llama `useNavigate()` con `-1` y `1`. Asi la asercion observa el
  historial real del router en vez de reimplementar su semantica en la prueba. La sonda vive en el
  archivo de test y no altera el producto.
- **Los destinos "proximamente" se distinguen por su contenido:** actividades y certificados
  comparten el encabezado `Proximamente`, asi que se distinguen por la descripcion de cada seccion.

/**
 * The backend is the authority of the profile, so the journey holds one person instead of a fixed
 * answer. Registering, signing in, restoring and updating all read the same mutable record, which is
 * what makes a profile edited in the form the one the next request returns.
 */
function createScenario() {
  const profile: { current: AuthenticatedUser } = { current: initialParticipant };
  const registered: { payload: RegistrationPayload | null } = { payload: null };

  const registration: RegistrationAdapter = {
    loadCatalog: vi.fn().mockResolvedValue(catalog),
    register: vi.fn((payload: RegistrationPayload) => {
      registered.payload = payload;

      return Promise.resolve({ userId: profile.current.id });
    }),
  };

  const auth: AuthAdapter = {
    changePassword: vi.fn().mockResolvedValue(undefined),
    loadCurrentUser: vi.fn().mockImplementation(() => Promise.resolve({ ...profile.current })),
    login: vi.fn().mockImplementation(({ email, password }) => {
      if (email !== profile.current.email || password !== PARTICIPANT_PASSWORD) {
        return Promise.reject(new Error("credenciales incorrectas"));
      }

      return Promise.resolve(journeyTokens);
    }),
    logout: vi.fn().mockResolvedValue(undefined),
    refresh: vi.fn().mockResolvedValue(journeyTokens),
    requestPasswordReset: vi.fn().mockResolvedValue(undefined),
    resetPassword: vi.fn().mockResolvedValue(undefined),
    updateCurrentUser: vi.fn().mockImplementation((_accessToken, request) => {
      profile.current = { ...profile.current, ...allowlistedProfilePatch(request) };

      return Promise.resolve({ ...profile.current });
    }),
    verifyEmail: vi.fn().mockResolvedValue(undefined),
  };

  return {
    adapters: { ...createAppAdapters({ source: "mock" }), auth, registration },
    auth,
    profile,
    queryClient: createQueryClient({ defaultOptions: { queries: { retry: false } } }),
    registered,
  };
}

/** Only the four contracted attributes ever reach the stored profile, mirroring the adapter allowlist. */
function allowlistedProfilePatch(request: ProfileUpdateRequest): Partial<AuthenticatedUser> {
  const patch: Partial<AuthenticatedUser> = {};

  if (request.firstName !== undefined) patch.firstName = request.firstName;
  if (request.lastName !== undefined) patch.lastName = request.lastName;

  if (request.unitId === null) {
    patch.career = { code: "OTROS", id: "otros", name: "Otros" };
    patch.unit = null;
  }

  if (typeof request.unitId === "string") {
    patch.unit = { code: "FISC", id: request.unitId, name: "Facultad de Ingenieria de Sistemas" };
  }

  return patch;
}

### Complete My Account Journey (`ACC-010`)

As an account holder, I want the whole account lifecycle to work in one continuous flow so that I am

Acceptance criteria:

pruebas unitarias y de integracion, 92 de Storybook entre `play`, axe y baseline visual, y el

### La fase no toco produccion

Los siete pasos del recorrido pasaron con el codigo que dejaron las fases 1.4 a 1.9. El unico cambio en
`src/` fuera de pruebas fue retirar un import sin usar que `typecheck` detecto en el propio archivo
nuevo. Ninguna correccion de producto resulto necesaria.

### Cuatro fallos fueron del arnen, ninguno del producto

1. **El formulario de registro aun cargaba el catalogo.** `registerThroughTheForm` consultaba el
   `combobox` de unidad de forma sincrona. Se cambio a `findByRole`, porque el catalogo resuelve de
   forma asincrona. Es el mismo fallo de arnes que la Fase 1.7 ya encontro en `ProfilePage`.
2. **La etiqueta del password del login era "Contrasena", sin tilde.** `LoginForm` rotulaba
   `Contrasena` y titulaba `Iniciar sesion en SIPEG`, mientras el resto de la aplicacion si usa
   tildes. El selector quedo en `/^contrasena$/i`, como ya hacia `App.test.tsx`. La correccion de
   copy se aplico despues, al cerrar el punto, y obligo a migrar los selectores; ver el bloque
   "Correccion De Copy Del Login" al final de este documento.
3. **El cliente de Query del escenario no era el de la app.** `signInAndOpenAccountData` montaba `App`
   sin pasar `scenario.queryClient`, de modo que `renderWithProviders` creaba otro y la prueba sembraba
   datos privados en un cliente que nadie limpiaba. La asercion de limpieza fallo con
   `expected { private: true } to be undefined`, que es exactamente el fallo que debia detectar. Se
   paso el cliente del escenario al montaje.
4. **Tras el logout el menu ya no ofrece "Mi perfil".** La asercion de que la URL personal se rechaza
   no podia pulsarse, porque el menu anonimo muestra "Iniciar sesion" y "Registrarse". Se sustituyo
   por un montaje limpio en `/perfil/datos` con el store ya anonimo, que es el caso real de quien
   escribe la direccion o pulsa atras. Ademas se fijo que el enlace personal desaparezca del menu.
