# Fase 3.4 - Descubrimiento de scopes

> **For agentic workers:** REQUIRED SUB-SKILL: Use `executing-plans` to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Consumir el contrato dedicado de descubrimiento de scopes (`GET /api/v1/users/me/scopes`) desde `features/collaboration`, sin N+1 sobre el catalogo publico, con adapter, mapper, clave por identidad y hook.

**Architecture:** La operacion vive en un adapter propio de `features/collaboration` que recorre las paginas con `limit=50` y valida cada payload antes de exponerlo. El hook `useUserScopes` liga la cache a la identidad del usuario, nunca al token, y no se persiste. No hay UI en esta fase: la navegacion por capacidad efectiva y `/operaciones` pertenecen a 3.5.

**Tech Stack:** React 19, TypeScript 6, Vitest, Testing Library, TanStack Query 5 y la CLI `api:contract`.

## Contrato originalmente ausente (2026-10-04, primera verificacion)

- El contrato vivo solo exponia `GET /api/v1/users/me/permissions?scope=program|activity&id=`, que
  responde por un scope conocido, no descubre.
- Con Bearer, `GET /event-programs` solo devolvia programas `ACTIVE` a quien no es ADMIN y
  `GET /activities` solo el conjunto publico: un colaborador no podia ver borradores ni archivados.
- El plan maestro del backend no planificaba la operacion en ninguna fase.
- Conclusion registrada entonces: 3.4 no era implementable y requeria un contrato dedicado. La
  propuesta quedo en `docs/adr/adr-0014-scope-discovery-contract.md`.

## Contrato publicado (2026-10-04, verificado con `api:contract`)

`GET /api/v1/users/me/scopes` con `bearerAuth`:

- Query: `type` opcional (`program|activity`), `page` (>=1, default 1) y `limit` (1..50, default 20).
- `UserScope`: `type`, `id`, `name`, `status` (enum unico `DRAFT/ACTIVE/COMPLETED/CANCELLED/ARCHIVED/
SCHEDULED/ONGOING`), `eventProgram` (`{id,name,label,status}|null`), `organizationalUnit`
  (`{id,name,type}`) y `permissions` (`OwnPermission`: `{name, origin, validFrom, validUntil}`).
- USER recibe sus colaboraciones directas; la actividad une la herencia del programa como
  `INHERITED`/`BOTH`. Se incluyen estados no publicos y se ignoran grants vencidos o futuros.
- ADMIN recibe el catalogo completo como `LOCAL` y sin envelopes. Orden `name ASC, id ASC`.
- Errores `400/401/403`; sin scopes responde pagina vacia, nunca `404`. Sin campos de auditoria.
- Desviacion respecto a ADR-0014: `status` es un unico enum combinado, no dos por tipo.

## Registro de ejecucion (2026-10-04)

- **Descubrimiento sin N+1:** la prueba del adapter entrega un programa `DRAFT` y una actividad `DRAFT`
  en la respuesta contractual, verifica que se expongan sin conocer sus IDs y que `fetch` se llame una
  sola vez por pagina. El mapper rechaza `type`, `status` y `origin` fuera del contrato.
- **Rama ADMIN del mock:** al iniciar sesion como ADMIN (mock), el mock deriva el catalogo completo,
  marca todos los permisos como `LOCAL` sin envelopes y conserva el orden `name ASC, id ASC`.
- **Privacidad:** la clave es `["user-scopes", userId, filters]`; `isPersistedQueryKey` es falso y no
  se toco `PERSISTED_QUERY_KEY_ROOTS` ni la version del esquema de cache.
- **Incidente operativo:** durante la ejecucion el backend dejo de servir la operacion entre dos
  consultas y `api:mocks-check` fallo con "la operacion ya no existe". Al volver el backend con la
  operacion publicada, la puerta paso; no se cambio ningun contrato ni codigo por ese fallo.
- **Puertas:** `format:check`, `lint`, `typecheck` en verde; suite completa 156 archivos y 1071
  pruebas; `api:mocks-check` con 221 verificaciones en 29 operaciones; `components:inventory:check`
  sin cambios (fase sin UI); `pnpm run check` ejecutado antes del cierre.
- **Sin Storybook:** no hay cambios visuales, de rutas ni de componentes.
- **Sin commit:** conforme a las reglas del repositorio.
