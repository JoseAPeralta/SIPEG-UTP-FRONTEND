# Fase 4.4–4.6 — Edición, ciclo de vida y programa predeterminado

> **For agentic workers:** REQUIRED SUB-SKILL: Use executing-plans to implement this plan
> task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Completar la administración de programas con edición, publicación `DRAFT -> ACTIVE`, archivo,
reactivación y el tratamiento de la agenda permanente dentro de `/admin/programas`.

**Architecture:** El panel vive en `EventProgramsView` y consume el registro ya validado del listado,
porque `GET /api/v1/event-programs/{id}` solo devuelve programas activos. El puerto
`EventProgramsAdapter` gana `updateEventProgram`, `archiveEventProgram` y `reactivateEventProgram`;
un hook `useEventProgramMutations` centraliza la invalidación. Ninguna mutación usa `DELETE`.

**Tech Stack:** React 19, TypeScript, TanStack Query, Chakra UI 3, Vitest, Testing Library, Storybook.

## Contrato verificado (2026-10-06, backend vivo)

| Operación                                     | Reglas                                                                                                                                                                                                                                                                                                                                       |
| --------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `PATCH /api/v1/event-programs/{id}`           | Bearer. Edita `name`, `description`, `label`, `bannerUrl`, `startDate`, `endDate`, `status`. `status` solo `const ACTIVE`, única transición `DRAFT -> ACTIVE`; cualquier otra responde `400/409`. Archivado responde `409`. Programa predeterminado con fechas responde `400`. Fechas que dejan actividades fuera del rango responden `409`. |
| `POST /api/v1/event-programs/{id}/archive`    | Bearer. Programa predeterminado con unidad activa responde `409`; adicional con actividades SCHEDULED/ONGOING no terminadas responde `409`; idempotente si ya está archivado.                                                                                                                                                                |
| `POST /api/v1/event-programs/{id}/reactivate` | Bearer. Solo adicionales archivados; predeterminado responde `409` (se reactiva desde la unidad); no archivado responde `409`; fechas incoherentes responden `400`; se admite con unidad inactiva.                                                                                                                                           |
| `GET /api/v1/event-programs/{id}`             | Público, solo programas ACTIVE; no sirve para editar borradores ni gestionar archivados.                                                                                                                                                                                                                                                     |

El `DELETE` existe en el contrato únicamente para responder que no está permitido: la UI jamás lo usa.

## Matriz de acciones

| Programa                                       | Acciones ofrecidas                        |
| ---------------------------------------------- | ----------------------------------------- |
| Adicional `DRAFT`                              | Editar, Publicar, Archivar                |
| Adicional `ACTIVE` / `COMPLETED` / `CANCELLED` | Editar, Archivar                          |
| Adicional `ARCHIVED`                           | Reactivar                                 |
| Predeterminado no archivado                    | Editar (sin fechas)                       |
| Predeterminado `ARCHIVED`                      | Enlace a la unidad, sin acciones directas |

```ts
import type { EventProgramListItem } from "./eventProgramList";

export type EventProgramLifecycleAction = "archive" | "edit" | "publish" | "reactivate";

/**
 * Acciones que la UI puede ofrecer para un programa. Evita controles incompatibles (editar un
 * archivado, publicar algo ya publicado, archivar la agenda permanente) y deja los rechazos de
 * negocio al contrato. La agenda permanente sin archivar solo se edita; su ciclo de vida pertenece
 * a la unidad.
 */
export function eventProgramLifecycleActions(
  program: Pick<EventProgramListItem, "isDefault" | "status">,
): EventProgramLifecycleAction[] {
  if (program.isDefault) return program.status === "ARCHIVED" ? [] : ["edit"];
  if (program.status === "ARCHIVED") return ["reactivate"];
  if (program.status === "DRAFT") return ["edit", "publish", "archive"];
  return ["edit", "archive"];
}
```

## Resultados y desviaciones

- **Contrato verificado contra el backend vivo (2026-10-06):** `PATCH /api/v1/event-programs/{id}`,
  `POST /api/v1/event-programs/{id}/archive`, `POST /api/v1/event-programs/{id}/reactivate` y
  `GET /api/v1/event-programs/{id}`. No se invento ningun campo, estado o transicion.
- **Decision de interfaz:** panel dentro de `/admin/programas`. El detalle contractual solo devuelve
  programas activos, de modo que borradores y archivados se gestionan con el registro validado del
  listado; no se creo una ruta de detalle ni una lectura administrativa inventada.
- **Modelo:** `UpdateEventProgramRequest` con allowlist, validacion de edicion separatada de la
  creacion y `eventProgramLifecycleActions` como matriz unica de acciones.
- **Puerto y adapters:** `updateEventProgram`, `archiveEventProgram` y `reactivateEventProgram` en API
  y mock; el mapper de envelope paso a `mapMutatedEventProgram` porque ahora sirve a las cuatro
  mutaciones. El mock reproduce los conflictos con la semilla determinista
  `eventProgramsWithRunningActivities` y valida fechas contra las actividades del fixture.
- **Invalidacion:** `useEventProgramMutations` refresca listado administrativo (prefijo), catalogo
  administrativo y agenda publica; la agenda permanente refresca el detalle de su unidad en ambas
  fronteras. Las mutaciones de unidad ahora invalidan tambien el listado independiente de programas.
- **Trampa de `mutateAsync` repetida:** `update(program, request)` habria interpretado `request` como
  opciones de la mutacion, el mismo defecto documentado en la Fase 2.4. La firma viaja dentro de un
  unico objeto y el hook expone un envoltorio de dos parametros.
- **Nombre accesible del boton en carga:** Chakra oculta el contenido al usar `loading` y el boton
  pierde su nombre. `EditEventProgramForm` y la confirmacion usan `loadingText`; el mismo criterio ya
  regia en `CreateEventProgramForm` desde 4.3.
- **Foco:** al cancelar vuelve al control de apertura; al completar, el foco pasa a la region del
  listado y el anuncio vive en un `StatusPanel`, siguiendo el precedente de la bandeja de alertas. La
  confirmacion usa `role="group"` con una etiqueta que nombra accion y programa; cada tarjeta es un
  `article` con el nombre del programa como etiqueta.
- **Puerto 6007 ocupado de nuevo:** la primera corrida de `storybook:test:affected` dejo un
  `http-server` huerfano y el script lo detecto; se detuvo el proceso antes de reintentar. Es una
  observacion mas del defecto ya documentado en fases anteriores.
- **Baselines:** se regeneraron los cuatro de `EventProgramsView` (las tarjetas ganaron acciones y
  notas de agenda permanente) y se crearon trece nuevos (`EditEventProgramForm` y las tres stories
  nuevas de la vista). Todos se revisaron como cambio visual intencional.
- **Defecto de aislamiento entre stories, detectado al cerrar:** el runner Jest de Storybook reutiliza
  el adapter mock del `preview` entre stories del mismo archivo, de modo que `EditingProgram`
  renombraba el programa que `ArchivingProgram` buscaba y ambas fallaban solo en la corrida completa.
  Se corrigio editando un programa que ninguna otra story referencia (`Cumbre de Energia y Redes
Inteligentes`) y esperando la lista con `findByRole` en `PermanentAgenda`. Las stories aisladas ya
  pasaban; el defecto era del estado compartido, no del producto.
