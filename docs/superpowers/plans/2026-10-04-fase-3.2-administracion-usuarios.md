# Fase 3.2 - Administracion de usuarios

> **For agentic workers:** REQUIRED SUB-SKILL: Use `executing-plans` to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Implementar el listado paginado con busqueda y filtros, el detalle, el alta y la edicion de usuarios sobre `UserAdapter`, con feedback accionable para duplicados, relaciones invalidas y las salvaguardas de autodesactivacion y ultimo ADMIN.

**Architecture:** `features/users` gana un adapter con lectura paginada filtrada en servidor (`page`/`limit`/`q`/`globalRole`/`isActive`/`unitId`/`careerId`) y comandos `getUser`, `createUser` y `updateUser`. Los DTO y allowlists viven en el adapter; los hooks (`useUsersPage`, `useUserDetail`, `useUserMutations`) administran Query, claves por identidad y filtros e invalidacion precisa. `UsersView` vive en `/admin/usuarios` y `UserDetailView` en `/admin/usuarios/:userId`. `loadUsers()` (todas las paginas) se conserva para el shell de certificados.

**Tech Stack:** React 19, TypeScript, Chakra UI 3, TanStack Query 5, Vitest, Testing Library, Storybook, adapters mock/API.

## Contrato verificado (backend vivo, 2026-10-04)

- `GET /api/v1/admin/users` (`bearerAuth`, `ADMIN`): `page` (default 1), `limit` (default 20, max 50), `globalRole` (`USER|ADMIN`), `isActive` (`"true"|"false"`), `unitId`, `careerId`, `q` (1..200, busca por nombre, correo o cedula sin distinguir mayusculas). Respuesta `PaginatedUsers`; omitir `isActive` devuelve todos los estados.
- `GET /api/v1/admin/users/{id}` (`bearerAuth`, `ADMIN`): `AdminUser`; `404`.
- `POST /api/v1/admin/users` (`bearerAuth`, `ADMIN`): body `AdminUserCreate` con `email`, `password` (12..20), `firstName` (2..100), `lastName` (2..100), `identificationNumber` (5..30), `isActive` (default true), `unitId` (nullable), `careerId` (opcional). Siempre crea rol `USER` y envia correo de verificacion. `201`, errores `400/401/403/409`.
- `PATCH /api/v1/admin/users/{id}` (`bearerAuth`, `ADMIN`): body con `globalRole`, `isActive`, `unitId` (nullable; null fuerza la carrera global "Otros"), `careerId`. Salvaguardas: solo una cuenta activa se promueve, la promocion no se combina con desactivacion, desactivar revoca sesiones, un administrador no se autodesactiva ni se autodegrada y el ultimo ADMIN activo no se degrada ni desactiva. `200`, errores `400/401/403/404/409`.
- No existe `DELETE`: el ciclo de vida se cierra con `PATCH { isActive }`.

## Evidencia y desviaciones

- **Contrato verificado contra el backend vivo el 2026-10-04:** `GET /api/v1/admin/users`,
  `POST /api/v1/admin/users`, `GET /api/v1/admin/users/{id}` y `PATCH /api/v1/admin/users/{id}`, todos
  con `bearerAuth` y rol `ADMIN`. El listado admite `page`, `limit` (max 50), `globalRole`, `isActive`
  (`"true"|"false"`), `unitId`, `careerId` y `q` (1..200). El alta siempre crea rol `USER`. El `PATCH`
  solo edita `globalRole`, `isActive`, `unitId` y `careerId`; `unitId: null` fuerza la carrera global
  "Otros". No existe `DELETE`.
- **Paginacion en servidor:** el adapter expone `loadUsersPage(filters, page)` con `limit=20`;
  `loadUsers()` (todas las paginas) se conserva solo para el resumen transitorio de certificados. La
  clave de Query incluye filtros y pagina, ligada al `userId`, nunca al token, y no se persiste.
- **Edicion limitada:** nombre, correo y cedula quedan en solo lectura. El detalle separa el cambio de
  rol/unidad/carrera de la desactivacion, que exige confirmacion explicita porque revoca sesiones.
- **Salvaguardas en el mock:** `user-1` representa al administrador en funciones (autodesactivacion y
  autodegradacion devuelven `409`), se agrego un usuario inactivo para la regla de promocion, los
  duplicados devuelven `409` y una carrera fuera de la unidad `400`.
- **Puertas:** `api:mocks-check` paso con 207 verificaciones en 27 operaciones; la suite completa,
  `format:check`, `lint`, `typecheck` y `components:inventory:check` quedaron verdes; las siete stories
  nuevas pasaron `play`, axe y comparacion visual, con 7 baselines creados y revisados.
