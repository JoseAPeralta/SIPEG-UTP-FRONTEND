# Fase 1.6 Perfil Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `executing-plans` to implement this plan
> task-by-task. Steps use checkbox (`- [x]`) syntax for tracking.

**Goal:** Permitir que un usuario autenticado consulte y edite su propio perfil en `/perfil`,
modificando unicamente nombres, unidad organizativa y carrera, sin permitir mass assignment sobre
email, rol, estado o identificadores.

**Architecture:** El perfil validado sigue viviendo solo en Zustand, tal como fija ADR-0009, y no se
duplica en TanStack Query ni se persiste. `AuthAdapter` incorpora `updateCurrentUser(accessToken,
request)`, que exige Bearer, reconstruye una allowlist de cuatro campos y devuelve el `UserProfile`
validado. Un hook lee el access token en el momento del envio y entrega la respuesta a
`replaceCurrentUser`, que preserva tokens rotados y descarta el resultado si la identidad cambio. El
formulario construye parches parciales y muestra correo, cedula y rol como texto informativo.

**Tech Stack:** React 19, TypeScript 6, Vite 8, Chakra UI 3, React Router 8, TanStack Query 5,
Vitest 5, Testing Library, Storybook 10.

**Estado:** ejecutado el 2026-09-29. Todas las casillas quedaron verificadas.

## Contrato Verificado

Consultado contra el backend vivo con `pnpm run api:contract -- get GET /api/v1/users/me --pretty` y
`pnpm run api:contract -- get PATCH /api/v1/users/me --pretty`.

`GET /api/v1/users/me`

- Requiere `security: [{ bearerAuth: [] }]`.
- `200`: `UserProfile` con `id`, `firstName`, `lastName`, `identificationNumber`, `email`,
  `globalRole`, `unit` y `career`; `unit` y `career` son `OrganizationReference` o `null`.
- Errores: `401`, `404`.

`PATCH /api/v1/users/me`

- Requiere `security: [{ bearerAuth: [] }]` y `requestBody.required: true`.
- Body: `firstName` (2-100), `lastName` (2-100), `unitId` (`string` 1-50 o `null`), `careerId`
  (`string` 1-50). Los cuatro campos son opcionales.
- `unitId: null` selecciona la opcion "Otro" y **fuerza la carrera global "Otros"**.
- `200`: `UserProfile` completo actualizado.
- Errores: `400`, `401`, `404`, `409`.

El OpenAPI no declara `additionalProperties: false` en el body del PATCH, pero el backend descarta
campos desconocidos y rechaza un body formado solo por ellos
(`users.schemas.ts:8-28` y `users.routes.test.ts:451-503`). Esa es evidencia auxiliar: el frontend
construye de todos modos su propia allowlist, porque los tipos de TypeScript no protegen en runtime.

### Decisiones

- **Ruta:** `/perfil`, nueva y canonica, protegida por `RequireSession` para `USER` y `ADMIN`. No se
  crea `/mi-cuenta` ni un alias, porque nunca fue una ruta implementada. Las fases posteriores se
  construiran sobre `/perfil`.
- **Origen del perfil:** el `currentUser` ya validado en el store. `/perfil` no dispara un segundo
  `GET /users/me`, para no duplicar la fuente de verdad ni abrir una ventana de PII en el servidor de
  estado.
- **Unidad "Otro":** se envia `unitId: null` y se **omite** `careerId`; la carrera se presenta
  bloqueada como "Otros" porque el backend la fuerza.
- **Sin carrera vacia:** el contrato no admite `careerId: null` para limpiar la carrera manteniendo la
  misma unidad, por lo que el formulario no ofrece esa opcion.
- **Unidad inactiva o ausente del catalogo:** la asignacion vigente se conserva como primera opcion
  para no perderla en silencio; solo las unidades activas se ofrecen como nuevas opciones.
- **`careerId` al cambiar de unidad:** si la unidad cambia y no se elige carrera, el frontend omite
  `careerId`, porque el backend ya limpia una carrera incompatible al cambiar de unidad.
- **Parche parcial:** solo viajan los campos que el usuario modifico. El backend rechaza un body
  vacio, y el boton permanece deshabilitado mientras no haya cambios.
- **Errores:** `400` `invalid`, `401` `unauthenticated`, `404` `notFound`, `409` `conflict`, y
  cualquier otro `unknown`. Ningun mensaje del backend se muestra.
- **Sin query keys ni persistencia:** es una mutacion efemmera sobre estado privado.
- **Sin cambio de login:** un `USER` sigue terminando en `/` tras iniciar sesion; ese destino se
  ajusta en 1.7.

```ts
function profileUpdateBody(request: ProfileUpdateRequest): Record<string, string | null> {
  const body: Record<string, string | null> = {};

  if (request.careerId !== undefined) body.careerId = request.careerId;

  if (request.lastName !== undefined) body.lastName = request.lastName;

async updateCurrentUser(accessToken: string, request: ProfileUpdateRequest) {
```

```ts
export function toProfileUpdateRequest(
  values: ProfileFormValues,
  original: ProfileUpdateRequest,
): ProfileUpdateRequest {
  const firstName = values.firstName.trim();
  const lastName = values.lastName.trim();
  const request: ProfileUpdateRequest = {};

  if (firstName !== original.firstName) request.firstName = firstName;
  if (lastName !== original.lastName) request.lastName = lastName;
  if (values.unitId !== original.unitId) request.unitId = values.unitId || null;
  if (values.unitId && values.careerId !== original.careerId) {
    request.careerId = values.careerId || undefined;
  }

  return request;
}
```

```ts
export function useProfile() {
  const { auth } = useAppAdapters();
  const mutation = useMutation({
    mutationFn: async (request: ProfileUpdateRequest) => {
      const { tokens } = useSessionStore.getState();

      if (!tokens) {
        throw new ProfileUpdateError("unauthenticated");
      }

      try {
        return await auth.updateCurrentUser(tokens.accessToken, request);
      } catch (error) {
        throw toProfileUpdateError(error);
      }
    },
    onSuccess: (currentUser) => {
      useSessionStore.getState().replaceCurrentUser(currentUser);
    },
  });

  return {
    failure: mutation.error ? toProfileUpdateError(mutation.error).failure : null,
    isPending: mutation.isPending,
    isSuccess: mutation.isSuccess,
    updateProfile: mutation.mutateAsync,
  };
}
```

## Pruebas De La Evidencia De Mass Assignment

La prueba de la Fase 1.6 pide que "no se pueden modificar email, rol, estado o identificadores
mediante mass assignment". El frontend lo demuestra de forma aislada en tres capas:

- el formulario solo produce parches con `firstName`, `lastName`, `unitId` y `careerId`;
- el adapter reconstruye el body propiedad por propiedad, por lo que una llamada con `email`,
  `globalRole`, `isActive`, `id` o `identificationNumber` inyectados en runtime no los transmite;
- el mock ignora esas mismas propiedades, de modo que Storybook y las pruebas no puedan materializar
  un perfil inconsistente.

Lo que **no** puede demostrar un test unitario del frontend es que otro cliente no llame directamente
al backend: esa garantia es del backend y esta cubierta por sus propias pruebas.

## Desviaciones Durante La Ejecucion

- **`NativeSelect.Field` no acepta `disabled`.** El atributo debe ir en `NativeSelect.Root` y, sobre
  todo, en `Field.Root disabled`, que es lo que deshabilita el control underlying. La primera
  implementacion solo usaba `NativeSelect.Root`, y la story de envio mostro el selector de unidad
  todavia activo. El mismo mecanismo ya lo usa `RegisterForm`.
- **Fixture de validacion incorrecto en la primera red.** `toProfileUpdateRequest` se probo con un
  formulario cuya unidad vacia no coincidia con el perfil original, de modo que todos los casos
  devolvian `unitId: null`. Corregido el fixture para que `original` represente el estado en forma de
  formulario.
- **Defecto real encontrado por la red:** con una unidad elegida y la carrera vacia, la funcion
  enviaba `careerId: ""`. Ahora la carrera solo viaja cuando tiene valor.
- **`maxLength` hace inalcanzable el error de longitud maxima.** El limite de 100 caracteres lo
  impone el propio `Input`, asi que la prueba de "nombre demasiado largo" no podia dispararse desde
  la UI. Se sustituyo por una asercion sobre el atributo `maxlength`; la rama del maximo sigue
  cubierta en `profileValidation.test.ts` para quien llame a la validacion desde otro punto.
- **`ProfileView` se prueba por el puerto, no mockeando el modulo.** En vez de sustituir
  `useRegistrationCatalog` con `vi.mock`, se inyecta un `RegistrationAdapter` espia. Asi se ejercita
  la integracion real del catalogo, incluidos los estados de carga, error y reintento, y se evita el
  `import()` type que prohibe la regla de imports consistentes.
- **`ProfileForm` se remonta con `key` en vez de sincronizar con un efecto.** Despues de un exito el
  store ya trae el perfil autoritativo; la vista pasa `key` derivada de los campos editables y el
  formulario vuelve a precargar sin un efecto que escriba estado.
- **Baselines visuales obsoletos, no regresiones.** `pnpm run test:storybook:update` tambien reescribio
  los baselines de `LoginForm` y de `AppMenu`, que seguian sin regenerar desde las fases 1.4 y 1.5
  porque ese trabajo aun no estaba commiteado. Se inspeccionaron las capturas antes de aceptarlas: la
  de `LoginForm` recupera el enlace de recuperacion y el boton de ancho correcto, y la del menu
  incorpora el enlace de 1.5 junto al nuevo de 1.6.
- **Puerto 6007 ocupado.** Un `http-server` huerfano de una corrida anterior impedia servir el
  catalogo estatico. Se detuvo el proceso antes de ejecutar las stories; el script lo detecta y falla
  con un mensaje explicito en lugar de validar contra un servidor ajeno.
