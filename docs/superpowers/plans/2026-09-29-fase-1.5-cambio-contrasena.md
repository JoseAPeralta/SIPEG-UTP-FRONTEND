# Fase 1.5 Cambio De Contrasena Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `executing-plans` to implement this plan
> task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Permitir que cualquier usuario autenticado cambie su contraseña con la contrasena actual y
la confirmacion de la nueva, conservando su sesion vigente y sin exponer tokens.

**Architecture:** Se amplia `AuthAdapter` con `changePassword(accessToken, payload)`, que exige Bearer
y valida el sobre `EmptyData` antes de exponerlo. Un hook lee los tokens de `useSessionStore` en el
momento del envio, compone el payload contractual y clasifica el fallo en vocabulario localizado.
El formulario recibe solo contrasenas; la pagina compone el hook, el formulario y el estado de
exito, y nunca presenta mensajes del backend.

**Tech Stack:** React 19, TypeScript 6, Vite 8, Chakra UI 3, React Router 8, TanStack Query 5,
Vitest 5, Testing Library, Storybook 10.

**Estado:** ejecutado el 2026-09-29. Todas las casillas quedaron verificadas.

## Contrato Verificado

Consultado con `pnpm run api:contract -- get POST /api/v1/auth/change-password` contra el backend
vivo. El buscador (`search "change password"`) no devuelve resultados, por lo que se consultedo la
ruta directamente.

`POST /api/v1/auth/change-password`

- Requiere `security: [{ bearerAuth: [] }]`.
- Body: `{ currentPassword: string (minLength 1), newPassword: string (minLength 12, maxLength 128),
refreshToken: string (minLength 1) }`, `required` con los tres campos.
- `200`: `{ success: true, message: string, data: EmptyData }`. Descripcion: _"Password updated.
  Every other session is revoked."_
- Errores: `400`, `401`, `403`, `429` con `ApiErrorResponse`.

### Decisiones

- **Ruta:** `/cambiar-contrasena`, disponible para `USER` y `ADMIN`. Es un destino personal
  complementario de `/perfil`.

  > **Nota de decision del 2026-09-29, registrada durante la Fase 1.6.** Al redactar esta fase el
  > destino futuro se llamaba `/mi-cuenta`. La Fase 1.6 creo `/perfil` como area personal canonica, y
  > la decision del usuario fue trabajar las fases siguientes sobre `/perfil`, de modo que
  > `/mi-cuenta` no llega a existir y no deja alias. La Fase 1.7 integrara el cambio de contrasena
  > como seccion de seguridad de `/perfil` sin cambiar su dominio ni su contrato, por lo que esta
  > ruta sigue siendo valida.

- **Guard:** se extrajo `RequireSession` de `RequireAdminSession`; el guard administrativo conserva
  su redirect a `/` para roles no `ADMIN`.
- **Tokens:** los lee `useChangePassword` desde `useSessionStore` en el momento del envio, nunca en
  el render, para que una rotacion programada no vuelva obsoleto el payload. El formulario no
  recibe tokens y no los renderiza.
- **Sesion:** el exito **no** limpia sesion, `QueryClient`, contexto de trabajo ni almacenamiento.
  El backend conserva la sesion identificada por el `refreshToken` recibido. Tampoco se navega ni se
  cierra la sesion tras el cambio.
- **Largo de contrasena:** se mantiene el maximo de **20 caracteres**, alineado con la recuperacion
  (decision del usuario), mas estricto que el `maxLength: 128` del contrato consultado en esta fase.

> **Nota de cierre del mismo dia.** El backend ajusto despues las tres operaciones de contrasena a
> `minLength: 12` y `maxLength: 20`, con lo que 20 paso a ser el limite contractual y no una decision
> mas estricta del frontend. `RegisterForm` se alineo al mismo rango y la politica 12-20 quedo
> compartida por registro, recuperacion y cambio.

- **`400` no se descompone:** contrasena actual incorrecta, refresh token ajeno y error de validacion
  son indistinguibles por contrato. La UI muestra un unico mensaje localizado.
- **Sin query keys:** es una mutacion efemmera; no se invalida ni se persiste nada.

```ts
export function useChangePassword() {
  const { auth } = useAppAdapters();
  const mutation = useMutation({
    mutationFn: async (request: PasswordChangeRequest) => {
      const { tokens } = useSessionStore.getState();

      if (!tokens) {
        throw new PasswordChangeError("unauthenticated");
      }

      try {
        await auth.changePassword(tokens.accessToken, {
          ...request,
          refreshToken: tokens.refreshToken,
        });
      } catch (error) {
        throw toPasswordChangeError(error);
      }
    },
  });

  return {
    changePassword: mutation.mutateAsync,
    failure: readFailure(mutation.error),
    isPending: mutation.isPending,
    isSuccess: mutation.isSuccess,
  };
}
```

## Pruebas De La Evidencia De Revocacion

La prueba de la Fase 1.5 pide que "las demas sesiones revocadas no pueden restaurarse". Lo que el
frontend puede demostrar de forma aislada es:

- que el `refreshToken` que se envia es el de la sesion actual, leido del store en el momento del
  envio;
- que el `accessToken` que se envia es el de la sesion actual;
- que la sesion actual, su `sessionStorage`, su `QueryClient` y su contexto de trabajo sobreviven al
  exito.

Lo que **no** puede demostrar un test unitario del frontend es que una segunda sesion real deje de
restaurarse: eso requiere dos sesiones contra el backend vivo. Queda como verificacion dirigida de
la Fase 1.9 o de la suite E2E de la Fase 12.

Ademas, la revocacion no invalida de inmediato un access token ya emitido: la otra pestana sigue
operando hasta que su proximo refresh es rechazado y su bootstrap limpia la identidad.
