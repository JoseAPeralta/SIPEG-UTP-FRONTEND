# Fase 5.11 — Publicación y privacidad de actividades

> **For agentic workers:** REQUIRED SUB-SKILL: Use `executing-plans` to implement this plan task-by-task. Steps use checkbox (`- [x]`) syntax for tracking. No crear commits salvo petición explícita del usuario.

**Goal:** demostrar con pruebas que cada identidad —visitante anónimo, `USER` colaborador y `ADMIN`— ve exactamente los estados que el contrato publica para ella, tanto en la agenda y el detalle públicos como en la administración privada, y corregir las fugas que esas pruebas expongan.

**Architecture:** la frontera pública (`PublicActivityCatalogAdapter`) no envía credenciales y valida estados publicables; la privada (`ActivitiesAdapter`, `UserScopesAdapter`) exige Bearer y claves ligadas a la identidad. La vista de detalle no debe presentar datos del detalle administrativo hasta que las capacidades confirmen `activity:read`, y una ventana de permiso vencida debe retirar la lectura sin esperar otra respuesta de red.

**Tech Stack:** React 19, TypeScript 6, TanStack Query 5, Vitest 5, Testing Library, Storybook 10, Playwright.

## Contrato verificado (2026-10-09, backend vivo)

| Operación                                    | Regla que la cobertura debe respetar                                                                                                                                                                                              |
| -------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /api/v1/activities`                     | Público con auth opcional. Anónimos y no-ADMIN reciben `SCHEDULED`/`ONGOING`/`COMPLETED` de programas activos; solo ADMIN puede filtrar `DRAFT`/`CANCELLED`/`ALL`; un Bearer inválido responde `401` y una cuenta inactiva `403`. |
| `GET /api/v1/activities/{id}`                | Público. Anónimos solo ven no-`DRAFT` de programas activos; Bearer de ADMIN o colaborador con `activity:read` lee borradores y programas no activos. Un `CANCELLED` conserva su enlace directo con `cancelReason`.                |
| `GET /api/v1/event-programs/{id}/activities` | Público. Anónimos solo ven estados públicos de programas activos; el filtro de estado se honra solo con ADMIN o `activity:read`; programas no activos responden `404` salvo autorización.                                         |
| `GET /api/v1/users/me/scopes`                | Bearer. Un `USER` recibe solo sus colaboraciones directas (programa o actividad); los permisos heredados viajan dentro del scope de actividad. ADMIN recibe el catálogo completo.                                                 |
| `PATCH /api/v1/activities/{id}`              | `activity:update` o ADMIN; `ONGOING`/`COMPLETED`/`CANCELLED` responden `409`; solo `status` `DRAFT`/`SCHEDULED`.                                                                                                                  |
| `POST /api/v1/activities/{id}/cancel`        | `activity:cancel` o ADMIN; cancela `DRAFT`/`SCHEDULED`/`ONGOING`; programa no activo o `COMPLETED` responden `409`; idempotente.                                                                                                  |
| `DELETE /api/v1/activities/{id}`             | `activity:delete` o ADMIN; solo `DRAFT` de programa `ACTIVE` sin asistencia ni alertas; `204` sin cuerpo.                                                                                                                         |

**Hallazgos que la fase corrige:**

1. `ActivityDetailView` carga el detalle antes de resolver las capacidades y usa `activity.name` como
   encabezado fuera del bloqueo de acceso. Un detalle cacheado de una sesión anterior o de un permiso
   vencido muestra el nombre privado junto a «Contexto no autorizado».
2. `useActivityCapabilities` evalúa las ventanas con `Date.now()` en el render, pero nada vuelve a
   renderizar cuando un permiso vence con la vista abierta; la lectura debe retirarse sola.
3. Defecto encontrado por la puerta: los dos hooks de filtros del catálogo envolvían en
   `startTransition` el estado que renderiza el input de búsqueda; bajo carga el commit se retrasa y
   se pierden pulsaciones. El estado del filtro pasa a actualizarse de forma urgente.
4. Defecto de arnés encontrado por la puerta: el runner visual resolvía `storyFinished` sin mirar su
   `status`, de modo que un `play` fallido podía capturarse y hasta congelarse como baseline. La
   baseline corrupta de `filtering-activities` se eliminó y regeneró.

## Matriz de visibilidad exigida

Para actividades de un programa `ACTIVE`:

| Estado      | Agenda pública | Detalle público por URL       | Detalle privado (`activity:read` o ADMIN) |
| ----------- | -------------- | ----------------------------- | ----------------------------------------- |
| `DRAFT`     | Oculta         | No disponible                 | Disponible                                |
| `SCHEDULED` | Visible        | Disponible                    | Disponible                                |
| `ONGOING`   | Visible        | Disponible                    | Disponible                                |
| `COMPLETED` | Visible        | Disponible                    | Disponible                                |
| `CANCELLED` | Oculta         | Disponible con aviso y motivo | Disponible                                |

Además: las actividades de programas no `ACTIVE` quedan fuera de la experiencia pública; la frontera
pública es idéntica para visitante, `USER` y `ADMIN`; el colaborador lee por scope de programa
(herencia) o por scope exacto de actividad; la caché persistida nunca incluye detalle público ni
ninguna lectura privada.
