# Fase 4.2 — Listado administrativo de programas

> **For agentic workers:** REQUIRED SUB-SKILL: Use `executing-plans` to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Entregar el listado administrativo de programas con búsqueda, unidad, estado y paginación del servidor.

**Architecture:** El puerto `EventProgramsAdapter` gana una lectura paginada propia, el hook `useEventProgramsPage` administra filtros y página sobre claves ligadas a identidad, y `EventProgramsView` compone la UI con los componentes compartidos. La ruta `/admin/programas` queda bajo el guard ADMIN y no toca la lectura completa de 4.1 ni la caché pública.

**Tech Stack:** TypeScript, React 19, TanStack Query 5, Chakra UI 3, Vitest, Testing Library y Storybook 10.

---

## Contrato y alcance

Consultado el 2026-10-06 mediante `pnpm run api:contract -- get GET /api/v1/event-programs`.

- `GET /api/v1/event-programs` es público con autenticación opcional. Sin Bearer devuelve ACTIVE; con Bearer solo ADMIN puede usar otros estados. Token inválido `401`; cuenta inactiva `403`; estado inválido `400`.
- Parámetros: `page` (mínimo 1), `limit` (máximo 50), `organizationalUnitId`, `unitType`, `status` (`DRAFT | ACTIVE | COMPLETED | CANCELLED | ARCHIVED | ALL`) y `q` (nombre o etiqueta, máximo 200).
- **Decisión aprobada:** la pantalla es solo ADMIN. Los colaboradores conservan el descubrimiento y la operación por `/operaciones`. El contrato no permite a un colaborador descubrir borradores mediante este listado.
- **Decisión aprobada:** no existen filtros por fecha en el contrato. Las fechas se muestran en cada resultado y el filtro de fechas queda registrado como pendiente contractual.
- El listado arranca en "Todos" (`status=ALL`) porque omitir `status` devuelve únicamente programas activos.
- `EventProgramDetail` contiene la unidad anidada (`id`, `name`, `type`): el listado la muestra sin consultar el catálogo de unidades.

## Evidencia de cierre — 2026-10-06

- Alcance aprobado por el usuario antes de implementar: listado ADMIN con busqueda, unidad, estado y
  paginacion; las fechas se muestran y el filtro por fechas queda como pendiente contractual.
- Contrato vivo reconfirmado con `pnpm run api:contract -- get GET /api/v1/event-programs`: estados
  no publicos solo para ADMIN, `status=ALL` disponible, `limit` maximo 50 y ausencia de parametros de
  fecha.
- TDD por capas: mapper de listado con unidad embebida, `loadEventProgramsPage` HTTP/mock, hook con
  clave por identidad, filtros y pagina, y vista con filtros, vacio, error y reintento.
- El fixture compartido gano un borrador y un archivado para que el panel muestre todos los estados;
  la lectura publica y la composicion del catalogo no cambian porque el puerto de 4.1 sigue filtrando
  ACTIVE. El mock reproduce la restriccion de estados por rol con `readGlobalRole`, inyectado desde
  ambos composition roots.
- La unidad viaja embebida en cada item, de modo que el listado no consulta el catalogo para
  etiquetar filas; esa consulta solo puebla el filtro y su fallo no oculta el listado, que ofrece
  reintento propio.
- Puertas: `verify:quick` verde (194 archivos, 1.341 pruebas); `api:mocks-check` verde (310
  verificaciones en 47 operaciones); `check` verde con build, 47 suites de Storybook (175 pruebas
  `play`), 175 comparaciones visuales con axe e inventario (47 componentes).
- Se crearon 3 baselines de `EventProgramsView` y se regeneraron 6 de `AdminMenu`/`AdminLayout` tras
  eliminarlos: la tolerancia `maxDiffPixelRatio: 0.01` podia enmascarar la nueva pildora "Programas",
  deuda ya observada en 1.7 y 1.9. Las capturas se revisaron antes de conservarlas.
- Desviacion menor, fuera del alcance funcional: la historia `UnreadAlertsIndicator › CurrentPage`
  fallo una vez bajo carga porque su `play` afirmaba `aria-current` sin esperar la navegacion del
  router. Se endurecio con `waitFor`, el mismo patron que usan las historias de `AdminMenu`; no hay
  cambio visual ni de producto.
- Incidencia de arnes: un `http-server` huerfano en el puerto 6007 sobrevivio a una corrida fallida de
  `storybook:test:affected` porque el script termina el proceso padre, no al hijo. Se detuvo a mano.
  Es la misma friccion registrada en 1.7 y 4.1 y merece su propia correccion.
